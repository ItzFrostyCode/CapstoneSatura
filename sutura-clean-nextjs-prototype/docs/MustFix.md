Costing fields (base, rush, customization, discount, BOM cost, labor cost, actual vs estimated)Alteration details as an embedded objectBulk member arrays embeddedLegacy payment fields (amountPaid, payment_receipt_image, payment_reference)Denormalized arrays (items[], tasks[], swatch_images[])Fix: These should be separate tables. Costing → OrderCostSheet. Alteration → AlterationDetail. Bulk → BulkOrderMember table.

RISK 2 — Dual status systems for appointments (MEDIUM)The Appointment type uses string literals like 'Scheduled' | 'Confirmed' | 'Completed' while the Order type uses 'READY_FOR_FITTING'. There is no FK linking an Appointment to its resulting Order. These are completely disconnected.

Fix: Add appointment_id FK on Order. Add order_id FK on Appointment (nullable, set when order is created from it).

RISK 3 — MeasurementProfile has 50+ fields, mostly nullable (MEDIUM)The current MeasurementProfile has separate flat fields for jacket measurements AND legacy flat fields AND backward compat fields — all on the same entity.

Fix: Create a MeasurementValue child table:

MeasurementProfile (1) → (M) MeasurementValueMeasurementValue: { profile_id, field_name, value_inches, value_cm }This eliminates 40+ nullable columns and makes adding new measurement fields trivial.

RISK 4 — BranchRole vs UserRole duplication (LOW-MEDIUM)UserRole = ADMIN | OWNER | STAFF | CUSTOMER | DESIGNER (platform-level) BranchRole = MANAGER | TAILOR | HELPER | CASHIER | INVENTORY (operational-level) ProductionSpecialization = Tailoring | Cutting | QC | ... (workflow-level)

These are three distinct concepts but are partially conflated in some UI components (e.g., Staff type uses roles: StaffRole[] which aliases UserRole).

Fix: Keep them strictly separate. UserRole = auth gate. BranchRole = branch assignment. ProductionSpecialization = task filter tag. No aliasing.

RISK 5 — Payment entity has dual job_order_id and invoice_id (MEDIUM)typescriptjob_order_id?: string;   // Direct payment to orderinvoice_id?: string;     // Payment via invoiceThis means a payment can belong to either an Order OR an Invoice — but not enforced which one must be present. This creates ambiguity in the billing audit trail.

Fix: Payment must always link to an Invoice. The Invoice always links to an Order. Remove job_order_id from Payment — traverse through Invoice.

RISK 6 — Supplier embedded items[] (LOW)Supplier.items?: string[] — this is a denormalized array of item SKUs embedded directly on the supplier. This was legacy and is now replaced by SupplierItem junction, but the old field remains in the type.

Fix: Remove items[] from Supplier type. Use SupplierItem exclusively.

RISK 7 — Invoice has 6+ alias fields (LOW)Invoice.order_id vs Invoice.job_order_id, Invoice.issueDate vs Invoice.issued_at, Invoice.dueDate vs Invoice.due_date. Legacy aliases from migration.

Fix: Pick one canonical field name per value. Remove all aliases after migration.

RISK 8 — SupportTicket.messages[] is embedded (MEDIUM)typescriptmessages: SupportTicketMessage[]This is currently stored as an embedded array — effectively JSON in the entity. For a relational system, this must be its own table.

Fix:

SupportTicket (1) → (M) SupportTicketMessageSupportTicketMessage: { id, ticket_id, sender_user_id, message, created_at }SupportTicketAttachment: { id, message_id, url, file_type, file_size }SECTION 8 — WHAT SHOULD STAY SEPARATESeparation Rule	ReasonDesignProposal must NOT be Order	Proposal is creative/review layer; Order is production/operational.
